## 二、目标行为

正式站点统一使用不带 www 的 HTTPS 地址：`https://v2grad.com`。

例如旧文章 `https://imzhanghao.com/2022/06/10/mlops/` 永久跳转至 `https://v2grad.com/2022/06/10/mlops/`。

迁移规则：

- 旧主站的 HTTP、HTTPS、www 和不带 www 入口，直接 301 到新站同一路径，保留查询参数。
- 新域名的 HTTP 和 www 入口，直接 301 到新域名的 HTTPS 非 www 对应路径。
- 新站有效页面返回 200；原本不存在的路径最终仍返回真实 404，不统一跳到首页。
- 旧站 HTTPS 证书持续有效，访问旧地址必须先完成 TLS 握手，才能收到跳转。
- 仅匹配主站域名，不能把 `oss.imzhanghao.com` 纳入通配跳转。
- robots.txt 和所有权验证文件按实际用途单独处理；旧域名 robots.txt 保持允许抓取。证书自动续期的验证路径也要兼容跳转规则。

DNS 负责把请求引到服务器，301 由 Nginx 实现。不要只修改 DNS，也不要依赖 iframe、JavaScript 或把所有旧文章转到新首页。

Bing：添加并验证新站，可采用 Google Search Console 导入或平台提供的验证方法。保留旧站，不能把旧站属性直接删除。当前官方可访问指南强调 301、canonical、sitemap 和 IndexNow；不把旧版 Site Move 工具作为迁移前提，执行时以实际后台可用入口为准。

## 四、代码与本地验证

本地改动范围：

| 文件或内容 | 计划改动 |
| --- | --- |
| `_config.yml` | url 改成 `https://v2grad.com`，permalink 不变 |
| `_config.fluid.yml` | 开启 canonical，检查生成结果 |
| `source/robots.txt` | sitemap 声明指向新域名 |
| `source/CNAME` | 若继续维护 GitHub Pages，则与该平台实际绑定计划同步更新 |
| 内容及模板 | 站内文章绝对链接、分享地址、OG 元信息、Feed 等改成新主站 |
| 自动推送和统计 | 检查站点地址、平台验证、授权及允许域名，避免继续向旧站提交新 URL |

禁止全仓替换 `imzhanghao.com`：图片 CDN、邮箱、历史描述、证书及服务器配置要分别判断。

先生成新站产物，在本地或受访问控制的预览环境验收。不要提前长时间公开两份可索引的完整站点。若使用临时 noindex，上线前必须确认已移除；robots.txt 禁止抓取不能代替访问控制，也不能可靠阻止 URL 被收录。

以旧 sitemap 清单批量检查新产物对应页面，重点覆盖搜索流量较高文章、分类、分页、中文及编码路径、Feed、静态资源。检查新 canonical、链接、sitemap 和页面内容一致。

品牌名可以按最终决定做小范围调整；文章标题、正文、URL 和主题保持稳定。

## 五、切换当天的顺序

以下均为待授权的生产动作，方案本身不代表执行授权。

1. 确认备案、DNS、证书及本地验收通过，选择低流量窗口。
2. 在同一服务器增加新域名独立 Nginx 站点和独立静态产物目录，保留旧产物，便于回退；不需要新增服务器。
3. 在公开切换前，用 hosts 或 curl --resolve 验证新域名 TLS、页面及资源，确认不会误命中旧站虚拟主机。
4. 新域名 DNS 生效并确认站点可正常访问后，启用旧主站逐页 301 与新域名规范化规则。先检查 Nginx 配置，再 reload。
5. 立即验证：旧主站各入口一次跳到新站最终地址；目标页面 200；无循环；查询参数保留；新旧证书均有效；图片 CDN 仍正常；404 正确。
6. 验证旧域名 robots.txt 可抓取、新站无 noindex，新 canonical、sitemap、Feed 及重要站内链接均正确。
7. 在旧 Google Search Console 站点的“设置 → 地址更改”提交迁移，按工具要求处理参与迁移的主站变体。新站提交新 sitemap。
8. Bing 新站提交新 sitemap，用 URL 检查验证代表页面。已有 IndexNow 能力时，按新域名完成验证后通知迁移发生的 URL；尚未接入时不将其作为切换门槛。
9. 更新自己可控制的 GitHub、社交资料及其他重要外链。不要删除旧搜索平台资源，不使用移除 URL 工具来加速迁移。

新 sitemap 仅列新站规范 URL。旧 sitemap 可归档为迁移对照；如保留旧地址 sitemap 作观察，应与新 sitemap 区分，旧 URL 被标记为“重定向页面”属于预期现象。

## 六、验收与观察

切换验收是技术可用性验收；搜索收录与排名转移需要后续时间，不能写成上线当天已完成。

| 时间 | 检查内容 |
| --- | --- |
| 当天 | 全部原 sitemap URL 映射，重要额外历史入口，200/301/404、TLS、canonical、robots、资源可用性 |
| 前 7 天 | 建议每日看一次两站抓取错误、重要 URL 检查、站点可用性与合计搜索点击；注意平台数据延迟 |
| 第 2 至 8 周 | 建议每周检查新旧站合计点击/展示、相同查询及页面组的变化、新站收录趋势 |
| 至少 1 年 | 保留旧主站永久跳转及证书；长期保留旧域名更适合已有外链和旧图片地址 |

观察上述频率只是建议，本次不创建自动化或后台轮询。URL 检查中的抓取成功不等于已经收录；不以 site: 搜索结果数量作为验收依据。

搜索恢复不承诺固定日期或零波动。旧站点击下降、新站点击上升是迁移过程的一部分，判断时关注二者合计以及相同页面、查询的变化。

## 七、回退方式

- 切换前：新站未通过验收时保持旧站原样，延后切换。
- 切换后：证书故障、大面积 404、跳转循环等技术故障优先在新站快速修复；不能迅速修复时恢复备份的旧站配置与产物、撤销旧站跳转。
- 若已提交 Google 地址更改，回退时一并按其官方撤销流程处理；评估缓存的 301 及新站回流规则，保证不会出现双向循环。
- 301 可能已被浏览器和搜索引擎缓存，回退不是瞬时恢复。不能因为数日排名波动反复切域名。
- 首次发布可给跳转设置较短的显式缓存策略，降低客户端长缓存造成的回退困难，稳定后调整；这不会消除已缓存跳转。

## 八、成本与时间

推荐复用当前服务器，仅新增虚拟主机与一份静态产物，不新增服务器或迁移存储。新增持续费用主要为新域名续费；旧域名、图片 CDN、原服务器继续保留。TLS 可用自动续期的免费证书，若使用商业证书则另计；具体价格以实际产品为准。

| 工作 | 估算 | 依赖及并行关系 |
| --- | --- | --- |
| 备案、实名认证及材料审核 | 按阿里云与管局实际审核，不承诺完成日期 | 关键外部等待，可与其余准备并行 |
| 代码调整、构建和链接核对 | 1 至 2 小时 | 可在等待备案时完成 |
| DNS、证书、Nginx 配置准备 | 1 至 2 小时 | 可与代码准备交错推进，需服务器权限 |
| 发布、全 URL 验证、两平台提交 | 1 至 2 小时 | 备案及全部准备通过后进行 |
| 后续观察 | 前一周每日约 5 至 10 分钟，之后每周约 10 至 20 分钟 | 搜索引擎重新处理通常需数周，可能更长 |

开发、配置和切换合计约 3 至 6 小时，不含备案、DNS/证书异常等待及搜索转移时间。
